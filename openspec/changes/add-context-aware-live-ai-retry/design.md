# 设计：带上下文的现场 AI 重试

## 概述

现场 AI 兜底保持“先单图分析”的现有行为。只有当 AI 明确返回“上下文不足”标记时，才进入上下文重试流程。上下文图片从已经匹配到的同一个 PPT 中选择，按页面顺序取目标页之前的若干页，并保证最后一张始终是当前题目页。

## 数据流

1. `Lesson.answer_questions()` 在原始答案为空时调用现场 AI 兜底。
2. 现场兜底定位当前问题、匹配 PPT 和目标 slide。
3. 先下载或复用当前题图，调用单图分析。
4. 如果返回答案数组，缓存并提交。
5. 如果返回 `[]`，视为没有可用答案，不触发上下文扩展。
6. 如果返回“上下文不足”，进入 3、5、7、9 张图片的递增重试。
7. 每次重试都从同一个 PPT 的 matched slide 顺序中选择前置页，准备图片后调用多图分析。
8. 任一重试返回答案数组即缓存并提交；全部失败则提示人工回答。

## 接口和边界

`AIAnswerAnalyzer` 负责和模型交互：

- 增加明确的返回分类，区分答案、空答案、上下文不足和 API 失败。
- 增加多图分析方法，例如 `analyze_slide_with_context(image_paths, target_slide_index)`。
- 多图 prompt 明确说明最后一张图片是目标题目页，前面的图片只用于上下文。

`Lesson` 负责现场资源组织：

- 根据当前问题匹配 PPT 和 slide。
- 从 matched PPT 的 slide 列表中选择上下文窗口。
- 下载或复用现场图片缓存。
- 控制最多 4 次上下文重试。
- 写入日志、缓存答案，并保持现有提交流程不变。

## 上下文窗口

初始单图失败且返回“上下文不足”后，依次尝试以下窗口：

- 第 1 次上下文重试：3 张图。
- 第 2 次上下文重试：5 张图。
- 第 3 次上下文重试：7 张图。
- 第 4 次上下文重试：9 张图。

如果目标页之前没有足够多页面，则使用可取得的全部前置页面加目标页。窗口只从同一个 presentation 的 fetched PPT 数据中选择，不跨 PPT 拼接。

## 错误处理

- 图片下载失败：记录具体 URL、HTTP 状态、content-type 和字节数，当前重试失败。
- API 请求失败：沿用现有重试策略，最终失败时不提交答案。
- 上下文仍不足：达到上限后记录“上下文不足已耗尽”，不提交答案。
- `[]`：表示没有可用答案，不进行上下文扩展，避免把无题页误判成需要更多图片。

## 日志

日志统一使用 `[现场AI兜底]` 前缀，至少包含：

- 单图分析返回分类。
- 每次上下文重试编号、目标图片数量、目标 slide 和选中的 slide 列表。
- 每张图片的来源：本地缓存或下载。
- 多图 AI 返回内容和分类。
- 最终结果：已获得答案、无答案、上下文重试耗尽或 API 失败。

## 测试策略

- 单图返回“上下文不足”，3 图重试返回答案，应缓存并提交。
- 多次返回“上下文不足”，超过 4 次后不提交。
- `[]` 不触发上下文扩展。
- 上下文页面必须来自同一个 matched presentation，并保持 PPT 数据顺序。
- 多图请求 payload 中图片顺序正确，最后一张是目标题图。
